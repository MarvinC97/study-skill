# Choose the representation by the knowledge relationship

Read when choosing or checking a visual. A clear paragraph is valid for a simple idea; HTML is a delivery format, not a requirement to draw every sentence.

| Relationship | Main form | Semantic check |
|---|---|---|
| Sequence / process | Flow with branches | Label order and decision conditions; show termination/failure when relevant |
| Data movement | Data-flow diagram | Name the payload, producer, receiver; distinguish data from control |
| Composition / hierarchy | Nested blocks or tree | A child is a component/category, not necessarily a prerequisite |
| Dependencies | Directed graph | Define arrow direction; allow multiple prerequisites, not forced into a tree |
| States / changed conditions | State diagram or interactive model | Define transitions and show what remains unchanged |
| Alternatives / before-after | Aligned comparison | Use the same criteria and disclose differing assumptions |
| Quantity / mathematical mechanism | Curve, numeric example, adjustable variable | Define units, domain, formula and assumptions; do not invent a numeric model |
| Trust / authority | Boundary diagram | Show which actor can authorize what, not merely spatial proximity |

Plan one primary form per learning point or tightly related cluster. Revise it during generation if the actual source calls for another form. Templates are starting points, not fixed lesson scripts. Build a bespoke disposable diagram/tool when it makes a difficult relationship clearer; do not build a new platform.

## Arrow contract

Every arrow type must mean one stated thing: execution order, data transfer, dependency, or causation. Use labels or a legend; style alone is insufficient. A sequence does not establish causation. A source containing a concept does not establish a dependency edge. Graph direction must agree with its legend and state schema.

For RAG, the question and retrieved passages enter the model. Do not draw an arrow implying permanent training on the entire knowledge base. If showing insufficient evidence handling, distinguish a desired/example policy from a guaranteed property of all RAG systems.

## Scope and fidelity

Name the phase being illustrated and disclose important omitted phases. Keep source-backed facts distinct from simplifying assumptions. Mark fictional numerical examples. Supplement, rather than silently replace, the source's meaningful distinctions. Provide text equivalents for important relationships and avoid color-only meaning.

## V3.1 controlled contrast

For a before/after or side-by-side explanation, label the changed variable, fixed conditions and observed difference. Use matched criteria and disclose confounders when more than one factor changes. One teaching contrast illustrates its stated mechanism; it does not prove a universal performance benefit. Retain a source anchor or mark the contrast as a tutor-authored fictional example.
